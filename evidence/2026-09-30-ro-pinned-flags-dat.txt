# Session 2026-09-30 (later still) — RO-pinned Flags.dat: mechanism works, decision unchanged

## The proposal

"I know what the file should look like — copy it and mount it into place read-only
before the write, so the write fails and the good content stays." Tested directly.

## Method

1. Took prod's (1.43.0) known-good `Flags.dat`:
   `e3cea60b5c4e2088ad2acf8ac33288a4`, 9776 bytes.
2. Bind-mounted it **read-only** over the test2 (1.43.4) target path on the host
   (test2's `/config` is itself a host bind mount, so no new container needed):
   ```
   mount --bind <scratch>/Flags.dat "plex/Library/Application Support/Plex Media Server/Cache/Flags.dat"
   mount -o remount,ro,bind "<same path>"
   ```
   Verified: `findmnt` shows `ro,...`; `touch` returns `Read-only file system`;
   md5 reads back as prod's `e3cea60b…`.
3. Restarted test2 and ran the standard A/B transcode request.

## Result — the mechanism works, the hypothesis does not

**The write failed cleanly and harmlessly**, exactly as proposed:

```
WARN  - Failed to rename ".../Cache/Flags.dat.tmp.e75d48b3-…" to ".../Cache/Flags.dat": Resource busy
ERROR - SafelyWriteFile: failed to write over ".../Cache/Flags.dat": Rename failed
```

No crash, no fallback, no service degradation — server ready in 14 s, and the
pinned prod content survived the boot intact.

**The transcode decision did not change:**

| | slot | encoder |
|---|---|---|
| 1.43.0 (prod) | `10de:1be1:1043:13f0@0000:01:00.0` | `h264_nvenc` |
| 1.43.4 + `Flags.dat` **pinned RO to prod's exact bytes** | `CPU` | `libx264` |

## What this proves

`Flags.dat`'s **content is not an input to the transcode decision.** Having the
server's own canonical good bytes present at that path, with the write reliably
blocked, changes nothing. Combined with the earlier finding that the file is
rewritten ~20 s after every boot, the file is confirmed to be **derived output
that nothing in the decision path reads back**.

Useful incidental detail: the server writes it via **temp-file + rename**
(`Flags.dat.tmp.<uuid>` → `Flags.dat`). That is why an RO pin fails safely rather
than corrupting anything — the original inode is never modified. Any future
attempt to freeze Plex state files can rely on this.

## Teardown

Bind mount unmounted, `findmnt` confirms no test mounts remain, test2's
`Flags.dat` restored from backup (`cba41fed…`) and regenerated by the server to
the same value, baseline re-verified (`Used slots for CPU is now 1` /
`encoder=libx264`). Prod never modified.

## Conclusion

Third independent method (after cache-copy and derivation-fingerprint) confirming
the gate is the **1.43.4 code path**. No file-state manipulation — supplying,
pinning, or protecting caches — can restore hardware transcoding. The remaining
lead is unchanged: `FeatureManager::f(bool)` in the 1.43.4 code path.
